# 非機能要件定義書作成ガイド

本ガイドは、DOC-104 非機能要件定義書の各項目に何をどこまで書くかを説明する。共通のルールは設計書作成規約（STD-003）に従う。

## 1. この設計書の役割

**システムは、どの程度の品質で動かなければならないか。**

| 項目 | 内容 |
|------|------|
| 目的 | 性能・可用性・セキュリティ・運用性・移行性などの非機能要件を定義する |
| 書かないこと | 要件を実現する構成・方式（→ DOC-201、DOC-207） |
| 作成条件 | 常に |
| 要否 | 必須（規模Sは DOC-101 に統合可） |
| ファイル単位 | プロジェクトで1ファイル |
| テンプレート | [非機能要件定義書_テンプレート](../02_テンプレート/要件定義/非機能要件定義書_テンプレート.md) |

## 2. 作成の流れ

| 項目 | 内容 |
|------|------|
| 作成する工程 | 要件定義 |
| 作成前に読むもの（入力情報） | DOC-001 プロジェクト概要書、DOC-101 要件定義書 |
| この設計書が正として定義するもの | 非機能要件（可用性、性能・拡張性、運用・保守性、移行性、セキュリティ、システム環境）と目標値 |
| 関連設計書 | DOC-201、DOC-207、DOC-401、DOC-501、DOC-503 |

## 3. 項目別の記載ガイド

記載例は、共通の題材「個人向けタスク管理Webアプリ TaskNote」に基づく（03_記載例 参照）。要否・情報源の記号は設計書項目定義書（STD-004）2.2 に従う。

| No | 項目 | 記載内容 | 要否 | 情報源 | 記載例 |
|----|----|----|----|----|----|
| 4.1 | 可用性 | 稼働時間、稼働率、計画停止、障害時の復旧目標（RTO/RPO） | ◎ | 正 | NFR-001｜稼働時間｜24時間（計画停止あり）｜稼働率 99%｜中 |
| 4.2 | 性能・拡張性 | 利用者数、データ量、応答時間、スループット、将来の増加見込み | ◎ | 正 | NFR-002｜応答時間｜一覧表示の応答時間｜95%が1秒以内｜中 |
| 4.3 | 運用・保守性 | 運用時間帯、監視、バックアップ、保守体制 | ◎ | 正 | NFR-003｜バックアップ｜データを日次で保存する｜7世代｜高 |
| 4.4 | 移行性 | 移行対象、移行方式、移行期間の制約 | ○ 移行あり | 正 | （移行なし） |
| 4.5 | セキュリティ | 認証、アクセス制御、データ保護、監査の要求水準 | ◎ | 正 | NFR-005｜通信の暗号化｜通信はすべて暗号化する｜TLS 1.2 以上｜高 |
| 4.6 | システム環境 | 利用端末・ブラウザ、設置場所、法令・規格 | ◎ | 正 | NFR-006｜対応ブラウザ｜主要ブラウザの最新版｜Chrome、Safari、Edge｜高 |
| 4.7 | ユーザビリティ・アクセシビリティ | 操作性、多言語対応、アクセシビリティ水準 | ○ UIあり | 正 | NFR-007｜レスポンシブ｜スマートフォン幅で操作できる｜幅 360px 以上｜中 |

## 4. 書き方のポイント

- すべての要件に測定できる目標値を書く。目標値がないと、テストで合否を判定できない。
- 決められない値は推測で書かず TBD とし、課題ID を付ける。
- 観点（可用性・性能・運用・移行・セキュリティ・環境）を漏れなく確認する。該当しない観点も「対象外」と書く。

## 5. よくある誤り

- 「十分な性能」「高い可用性」のような曖昧な表現。
- 実現方式（冗長構成など）を書く → システム構成設計書に書く。

## 6. レビュー観点

設計書作成規約（STD-003）14.2 の共通レビュー観点に加えて、次を確認する。

| No | 確認内容 |
|----|----------|
| 1 | すべての要件に目標値があるか。 |
| 2 | 観点の漏れがないか。 |
| 3 | プロジェクトの予算・制約と矛盾する目標値になっていないか。 |

## 7. 小規模（規模S）での簡略化

規模Sでは要件定義書の1章として、重要なものだけを書いてよい。
