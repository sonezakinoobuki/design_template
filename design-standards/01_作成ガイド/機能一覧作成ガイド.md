# 機能一覧作成ガイド

本ガイドは、DOC-103 機能一覧の各項目に何をどこまで書くかを説明する。共通のルールは設計書作成規約（STD-003）に従う。

## 1. この設計書の役割

**システムは、どのような機能を持つか（機能IDの台帳）。**

| 項目 | 内容 |
|------|------|
| 目的 | システムが提供する機能を一覧化し、機能IDを採番する。以降の設計の起点とする |
| 書かないこと | 各機能の詳細仕様（→ 画面・API・処理設計書） |
| 作成条件 | 常に |
| 要否 | 必須 |
| ファイル単位 | プロジェクトで1ファイル |
| テンプレート | [機能一覧_テンプレート](../02_テンプレート/要件定義/機能一覧_テンプレート.md) |

## 2. 作成の流れ

| 項目 | 内容 |
|------|------|
| 作成する工程 | 要件定義 |
| 作成前に読むもの（入力情報） | DOC-101 要件定義書、DOC-102 業務フロー図 |
| この設計書が正として定義するもの | 機能ID、機能名、機能概要、対応要件ID、実現手段（画面・API・バッチ等）、優先度 |
| 関連設計書 | DOC-202、DOC-203、DOC-205、DOC-206、DOC-301 |

## 3. 項目別の記載ガイド

記載例は、共通の題材「個人向けタスク管理Webアプリ TaskNote」に基づく（03_記載例 参照）。要否・情報源の記号は設計書項目定義書（STD-004）2.2 に従う。

| No | 項目 | 記載内容 | 要否 | 情報源 | 記載例 |
|----|----|----|----|----|----|
| 4.1 | 機能分類 | 大分類・中分類（サブシステム、業務領域） | ◎ | 正 | 会員管理｜認証｜会員登録とログイン |
| 4.2 | 機能一覧 | 機能ID（FNC）、機能名、概要、優先度、リリース区分 | ◎ | 正 | FNC-002｜会員管理｜認証｜ログイン｜メールアドレスとパスワードで認証する｜REQ-002｜画面、API｜SCR-001、API-001｜会員｜高｜初回 |
| 4.3 | 対応要件 | 機能ごとの要件ID（REQ） | ◎ | 参照(DOC-101) | REQ-002 |
| 4.4 | 実現手段 | 画面／API／バッチ／帳票／外部連携の区分と要素ID（SCR、API、BAT、RPT、IF） | ◎ | 参照(各設計書) | 画面、API｜SCR-001、API-001 |
| 4.5 | 利用アクター | 機能を使うアクター（権限の詳細は DOC-207） | ◎ | 参照(DOC-101) | 会員 |

## 4. 書き方のポイント

- 機能ID はここで採番し、以降のすべての設計書がこの ID を参照する。機能一覧は設計の起点である。
- 1つの機能は、利用者から見て1つの目的を達成する単位にする。
- 要素ID 列は、画面・API などを設計した後に埋める。最初は実現手段だけでよい。

## 5. よくある誤り

- 画面単位で機能を分ける（1機能が複数画面にまたがることはよくある）。
- 権限の詳細を書く → セキュリティ設計書の権限マトリクスに書く。

## 6. レビュー観点

設計書作成規約（STD-003）14.2 の共通レビュー観点に加えて、次を確認する。

| No | 確認内容 |
|----|----------|
| 1 | すべての要件（REQ）がいずれかの機能に対応しているか。 |
| 2 | すべての機能に対応要件があるか（要件にない機能を作っていないか）。 |
| 3 | 要素ID 列が設計後に埋まっているか。 |

## 7. 小規模（規模S）での簡略化

規模にかかわらず必須。規模Sでは分類を1階層にしてよい。
