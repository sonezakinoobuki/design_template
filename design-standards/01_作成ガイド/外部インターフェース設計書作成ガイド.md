# 外部インターフェース設計書作成ガイド

本ガイドは、DOC-205 外部インターフェース設計書の各項目に何をどこまで書くかを説明する。共通のルールは設計書作成規約（STD-003）に従う。

## 1. この設計書の役割

**外部システムと、何を、いつ、どの方式でやり取りし、失敗時はどうするか。**

| 項目 | 内容 |
|------|------|
| 目的 | 外部システム・外部サービスとの連携方式・データ形式・タイミング・異常時の取り決めを定義する |
| 書かないこと | 自システムが提供する API の仕様（→ DOC-203） |
| 作成条件 | 外部システム・外部サービスと連携するシステム |
| 要否 | 条件付き必須（規模Sは DOC-201 に統合可） |
| ファイル単位 | 連携先ごとに1ファイル |
| テンプレート | [外部インターフェース設計書_テンプレート](../02_テンプレート/基本設計/外部インターフェース設計書_テンプレート.md) |

## 2. 作成の流れ

| 項目 | 内容 |
|------|------|
| 作成する工程 | 基本設計 |
| 作成前に読むもの（入力情報） | DOC-103 機能一覧、DOC-201 システム構成設計書 |
| この設計書が正として定義するもの | 連携先一覧、連携方式、データ項目、連携タイミング、エラー・リトライ方針 |
| 関連設計書 | DOC-201、DOC-301 |

## 3. 項目別の記載ガイド

記載例は、共通の題材「個人向けタスク管理Webアプリ TaskNote」に基づく（03_記載例 参照）。要否・情報源の記号は設計書項目定義書（STD-004）2.2 に従う。

| No | 項目 | 記載内容 | 要否 | 情報源 | 記載例 |
|----|----|----|----|----|----|
| 4.1 | 連携先概要 | IF ID、連携先、管理者・連絡先、連携の目的、方向（送信／受信） | ◎ | 正 | IF-001｜メール配信サービス｜サービス提供元｜期限通知メールの送信｜送信 |
| 4.2 | 連携方式 | プロトコル、API・ファイル・メッセージキューの別、同期・非同期 | ◎ | 正 | HTTPS｜API｜非同期 |
| 4.3 | 連携タイミング | リアルタイム、定時（スケジュールは DOC-501）、イベント契機 | ◎ | 正 | 毎朝のバッチ｜8:00（スケジュールは運用設計書） |
| 4.4 | 認証 | 連携先との認証方式（鍵の値は書かない） | ◎ | 正 | APIキー（保管場所はセキュリティ設計書 4.8） |
| 4.5 | データ項目 | 項目、型、必須、自システム項目との対応（マッピング） | ◎ | 正 | 1｜宛先｜string｜必須｜members.email｜— |
| 4.6 | エラー・リトライ | 異常の検知、リトライ回数・間隔、通知先、手動リカバリ方法 | ◎ | 正 | 送信失敗｜HTTPステータス 5xx｜3回・5分間隔｜開発者｜翌日再送 |
| 4.7 | 制約・取り決め | 流量制限、利用料金、SLA、連携先の仕様書の版数 | ○ 該当時 | 正 | 流量制限：100通/日（無料枠） |

## 4. 書き方のポイント

- 連携先の仕様書の版数を必ず書く。連携先の仕様変更に気づけるようにする。
- 失敗時の扱い（リトライ・通知・手動リカバリ）を必ず決める。外部連携は失敗する前提で設計する。
- 自システムが公開する API の仕様は API設計書に書き、本書には連携先ごとの取り決めだけを書く。

## 5. よくある誤り

- APIキーなどの秘密情報の値を書く。
- 連携先の仕様書を丸ごと転記する（参照と、使う部分だけを書く）。

## 6. レビュー観点

設計書作成規約（STD-003）14.2 の共通レビュー観点に加えて、次を確認する。

| No | 確認内容 |
|----|----------|
| 1 | エラー・リトライの方針があるか。 |
| 2 | データ項目の自システム側の対応先が明確か。 |
| 3 | 流量制限・料金などの制約を確認したか。 |

## 7. 小規模（規模S）での簡略化

規模Sではシステム構成設計書の1章として、連携先ごとに表1つ程度で書いてよい。
