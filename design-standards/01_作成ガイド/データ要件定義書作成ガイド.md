# データ要件定義書作成ガイド

本ガイドは、DOC-105 データ要件定義書の各項目に何をどこまで書くかを説明する。共通のルールは設計書作成規約（STD-003）に従う。

## 1. この設計書の役割

**システムは、どのようなデータを、どのような意味と関係で扱うか。**

| 項目 | 内容 |
|------|------|
| 目的 | システムが扱うデータの種類・意味・関係（概念データモデル）を定義する |
| 書かないこと | テーブル・カラムの物理定義（→ DOC-204） |
| 作成条件 | 永続データを持つシステム |
| 要否 | 条件付き必須（規模Sは DOC-101 に統合可） |
| ファイル単位 | プロジェクトで1ファイル |
| テンプレート | [データ要件定義書_テンプレート](../02_テンプレート/要件定義/データ要件定義書_テンプレート.md) |

## 2. 作成の流れ

| 項目 | 内容 |
|------|------|
| 作成する工程 | 要件定義 |
| 作成前に読むもの（入力情報） | DOC-101 要件定義書、DOC-102 業務フロー図 |
| この設計書が正として定義するもの | エンティティ、エンティティ間の関係、データの保持期間・量の見込み、データ項目辞書（ドメイン：型・桁・形式の論理定義）、状態遷移、コード値の論理定義（値と意味） |
| 関連設計書 | DOC-204 DB設計書 |

## 3. 項目別の記載ガイド

記載例は、共通の題材「個人向けタスク管理Webアプリ TaskNote」に基づく（03_記載例 参照）。要否・情報源の記号は設計書項目定義書（STD-004）2.2 に従う。

| No | 項目 | 記載内容 | 要否 | 情報源 | 記載例 |
|----|----|----|----|----|----|
| 4.1 | エンティティ一覧 | エンティティID（ENT）、名称、定義、発生源、保持期間、件数見込み | ◎ | 正 | ENT-002｜タスク｜会員が管理する作業の単位｜会員の入力｜完了後1年｜1万件 |
| 4.2 | 概念ER図 | エンティティ間の関係（多重度） | ◎ | 正 | 会員 \|\|--o{ タスク |
| 4.3 | 主要属性 | エンティティの主要な属性と業務上の意味 | ◎ | 正 | ENT-002｜期限｜タスクを完了すべき日 |
| 4.4 | データ項目辞書（ドメイン） | 共通的に使う項目の型・桁・形式（例：メールアドレス、金額、電話番号）の論理定義 | ◎ | 正 | メールアドレス｜文字列｜254｜RFC 5322 準拠の形式｜user@example.com |
| 4.5 | 状態遷移 | 状態を持つエンティティの状態と遷移条件（例：注文ステータス） | ○ 該当時 | 正 | 未着手 → 完了｜完了ボタンを押したとき |
| 4.6 | コード定義 | 区分値・コード値の論理定義（値と意味） | ○ 該当時 | 正 | タスク状態｜1｜未着手｜1 |
| 4.7 | データの取り扱い区分 | 個人情報・機密情報の該当有無 | ◎ | 正 | ENT-001 会員｜有（メールアドレス）｜無｜— |

## 4. 書き方のポイント

- ここではテーブルではなく、業務上のデータのまとまり（エンティティ）を考える。
- データ項目辞書（ドメイン）は、画面・API・DB が共通で参照する型・桁の定義である。ここで決めると3か所の食い違いを防げる。
- 状態を持つデータ（注文、申請など）は状態遷移図を書く。画面の表示切り替えや処理の条件の元になる。

## 5. よくある誤り

- 物理名・データ型（VARCHAR など）を書く → DB設計書に書く。
- 画面ごとに異なる桁数を定義する。

## 6. レビュー観点

設計書作成規約（STD-003）14.2 の共通レビュー観点に加えて、次を確認する。

| No | 確認内容 |
|----|----------|
| 1 | 要件に出てくるデータがすべてエンティティになっているか。 |
| 2 | 個人情報の該当が判定されているか。 |
| 3 | コード値の意味が定義されているか。 |

## 7. 小規模（規模S）での簡略化

規模Sでは要件定義書の1章として、エンティティ一覧・ER図・ドメインだけを書いてよい。
