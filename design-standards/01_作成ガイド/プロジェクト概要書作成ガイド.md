# プロジェクト概要書作成ガイド

本ガイドは、DOC-001 プロジェクト概要書の各項目に何をどこまで書くかを説明する。共通のルールは設計書作成規約（STD-003）に従う。

## 1. この設計書の役割

**このプロジェクトは、なぜ、何を、どこまでやるのか。**

| 項目 | 内容 |
|------|------|
| 目的 | プロジェクトの背景・目的・スコープ・体制・制約を定義し、すべての設計書の前提を示す |
| 書かないこと | 個別の要件（→ DOC-101）、スケジュールの詳細（プロジェクト管理文書） |
| 作成条件 | 常に |
| 要否 | 必須 |
| ファイル単位 | プロジェクトで1ファイル |
| テンプレート | [プロジェクト概要書_テンプレート](../02_テンプレート/共通/プロジェクト概要書_テンプレート.md) |

## 2. 作成の流れ

| 項目 | 内容 |
|------|------|
| 作成する工程 | 共通 |
| 作成前に読むもの（入力情報） | 企画内容、ステークホルダーの要望 |
| この設計書が正として定義するもの | 背景、目的、スコープ（対象・対象外）、ステークホルダー、前提条件、制約条件、成功基準 |
| 関連設計書 | DOC-101 要件定義書 |

## 3. 項目別の記載ガイド

記載例は、共通の題材「個人向けタスク管理Webアプリ TaskNote」に基づく（03_記載例 参照）。要否・情報源の記号は設計書項目定義書（STD-004）2.2 に従う。

| No | 項目 | 記載内容 | 要否 | 情報源 | 記載例 |
|----|----|----|----|----|----|
| 4.1 | 背景 | プロジェクトに至った経緯、現状の課題 | ◎ | 正 | 紙のメモでタスクを管理しており、期限切れに気づけないことが多い |
| 4.2 | 目的・ゴール | 達成したいこと | ◎ | 正 | 期限付きタスクを一か所で管理し、期限切れを減らす |
| 4.3 | 成功基準 | ゴール達成を判断する指標と目標値 | ◎ | 正 | 期限切れタスクの割合｜10%以下｜月末時点の集計 |
| 4.4 | スコープ | 対象・対象外（業務、システム、組織） | ◎ | 正 | システム：TaskNote の Web 版／対象外：スマートフォンアプリ |
| 4.5 | ステークホルダー | 関係者、役割、関心事 | ◎ | 正 | 開発者（本人）｜設計・実装・運用｜作業量を抑えたい |
| 4.6 | システム概要 | システムの位置付けを示す概要図（コンテキスト図） | ◎ | 正 | 利用者 → TaskNote → メール配信サービス の関係図 |
| 4.7 | 前提条件 | プロジェクト全体の前提 | ◎ | 正 | 利用者はモダンブラウザを使う |
| 4.8 | 制約条件 | 予算、期間、技術、法令などの制約 | ◎ | 正 | 期間：3か月以内／予算：月額1,000円以内のクラウド費用 |
| 4.9 | 体制 | 役割と担当（個人開発は省略可） | △ | 正 | （個人開発のため省略） |
| 4.10 | マイルストーン | 主要な節目のみ（詳細スケジュールはプロジェクト管理文書） | △ | 正 | 初回リリース｜2027-03-01｜FNC-001〜004 が動作する |

## 4. 書き方のポイント

- 他の設計書の前提になるため、最初に作り、要件定義の前に確定させる。
- スコープは「対象外」を必ず書く。後から範囲が広がるのを防ぐ最も効果的な手段である。
- 成功基準は測定できる指標にする。「使いやすくする」ではなく「期限切れ率10%以下」のように書く。

## 5. よくある誤り

- 個別の要件（〜できること）を書いてしまう → 要件定義書に書く。
- 詳細なスケジュールを書く → プロジェクト管理文書で扱う。

## 6. レビュー観点

設計書作成規約（STD-003）14.2 の共通レビュー観点に加えて、次を確認する。

| No | 確認内容 |
|----|----------|
| 1 | 目的と成功基準が対応しているか。 |
| 2 | スコープの対象外が明記されているか。 |
| 3 | 制約条件に予算・期間・技術の観点が漏れていないか。 |

## 7. 小規模（規模S）での簡略化

個人開発では 4.9 体制・4.10 マイルストーンを省略してよい。1ページ程度で十分である。
