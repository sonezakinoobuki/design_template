# 設計書適用台帳作成ガイド

本ガイドは、DOC-002 設計書適用台帳の各項目に何をどこまで書くかを説明する。共通のルールは設計書作成規約（STD-003）に従う。

## 1. この設計書の役割

**このプロジェクトでは、どの設計書を、どう作り、今どの状態か。**

| 項目 | 内容 |
|------|------|
| 目的 | 本プロジェクトで作成する設計書・作成しない設計書と、その理由・状態を管理する |
| 書かないこと | 各設計書の内容 |
| 作成条件 | 常に |
| 要否 | 必須 |
| ファイル単位 | プロジェクトで1ファイル |
| テンプレート | [設計書適用台帳_テンプレート](../02_テンプレート/共通/設計書適用台帳_テンプレート.md) |

## 2. 作成の流れ

| 項目 | 内容 |
|------|------|
| 作成する工程 | 共通 |
| 作成前に読むもの（入力情報） | 本書（STD-002）の要否判断基準、プロジェクト概要書 |
| この設計書が正として定義するもの | 作成対象の設計書一覧、省略・統合の理由、テイラリング内容、各設計書の状態・版数 |
| 関連設計書 | すべての設計書 |

## 3. 項目別の記載ガイド

記載例は、共通の題材「個人向けタスク管理Webアプリ TaskNote」に基づく（03_記載例 参照）。要否・情報源の記号は設計書項目定義書（STD-004）2.2 に従う。

| No | 項目 | 記載内容 | 要否 | 情報源 | 記載例 |
|----|----|----|----|----|----|
| 4.1 | 規模区分 | S/M/L の判定結果と判定理由 | ◎ | 正 | 開発者数 1名、機能数 4、期間 3か月 → 規模S |
| 4.2 | システム特性 | UI有無、API提供、永続データ、外部連携、帳票、本番運用、移行の有無 | ◎ | 正 | UIを持つ｜有／既存データからの移行｜無 |
| 4.3 | 設計書適用一覧 | DOC-ID、設計書名、適用区分（作成／統合／省略）、統合先、省略理由、状態、版数、配置場所 | ◎ | 正 | DOC-104 非機能要件定義書｜統合｜DOC-101｜—｜作成中 |
| 4.4 | テイラリング内容 | 標準からの変更点と理由（項目追加、分割、ID方式など） | ◎ | 正 | 1｜画面設計書の 4.9 を削除｜フレームワーク標準に従うため |
| 4.5 | ID採番方式 | 連番桁数、サブシステム区分方式（STD-003 6.4） | ○ 大規模 | 正 | 連番桁数：3桁 |
| 4.6 | 標準への改善要望 | 適用中に気づいた標準の不足・過剰 | △ | 正 | 1｜画面設計書にアクセシビリティ項目がほしい｜STD-004｜未対応 |

## 4. 書き方のポイント

- プロジェクト開始時に STD-002 5.3 の要否判断フローに沿って作る。
- 省略・統合した設計書も一覧から消さず、理由を書く。後から「検討漏れ」と区別できる。
- 4.6 は標準を育てるための記録である。使っていて困ったことは小さなことでも書く。

## 5. よくある誤り

- 作成する設計書だけを書き、省略したものを書かない。
- 状態・版数を更新しない（台帳が実態とずれる）。

## 6. レビュー観点

設計書作成規約（STD-003）14.2 の共通レビュー観点に加えて、次を確認する。

| No | 確認内容 |
|----|----------|
| 1 | 24種すべてについて適用区分が決まっているか。 |
| 2 | 省略・統合の理由が要否判断基準と矛盾しないか。 |

## 7. 小規模（規模S）での簡略化

テンプレートの 4.3 に全24種が並んでいるので、適用区分と理由を埋めるだけでよい。
