# DB設計書作成ガイド

本ガイドは、DOC-204 DB設計書の各項目に何をどこまで書くかを説明する。共通のルールは設計書作成規約（STD-003）に従う。

## 1. この設計書の役割

**データは、どのテーブルに、どの構造・制約で保存されるか。**

| 項目 | 内容 |
|------|------|
| 目的 | 永続データの論理・物理構造を定義する |
| 書かないこと | データの業務的な意味の説明（→ DOC-105、DOC-003）、データを操作する処理（→ DOC-301） |
| 作成条件 | 永続データを持つシステム |
| 要否 | 条件付き必須 |
| ファイル単位 | ER図・テーブル一覧で1ファイル、テーブルごとに1ファイル。基本設計で論理設計、詳細設計で物理設計を同じファイルに追記する |
| テンプレート | [テーブル一覧_テンプレート](../02_テンプレート/基本設計/テーブル一覧_テンプレート.md)、[DB設計書_テンプレート](../02_テンプレート/基本設計/DB設計書_テンプレート.md) |

## 2. 作成の流れ

| 項目 | 内容 |
|------|------|
| 作成する工程 | 基本設計 |
| 作成前に読むもの（入力情報） | DOC-105 データ要件定義書 |
| この設計書が正として定義するもの | ER図、テーブル一覧、テーブル定義（カラム・型・制約・インデックス）、コード値の格納方式 |
| 関連設計書 | DOC-203、DOC-301 |

## 4. 書き方のポイント

- 基本設計で論理（4.1〜4.2）、詳細設計で物理（4.3〜4.7）を同じファイルに追記する。
- カラムの型・桁はデータ要件定義書のドメインに従う。テーブルごとに独自の桁を決めない。
- インデックスは「どの処理を速くするためか」を目的欄に書く。
- マイグレーションファイルがある場合は、それを正とし、設計書は概要と意図を書く。

## 5. よくある誤り

- 業務上の意味の説明を長く書く → データ要件定義書・用語集を参照する。
- コード値の意味をここで定義する → データ要件定義書のコード定義を参照する。

## 6. レビュー観点

設計書作成規約（STD-003）14.2 の共通レビュー観点に加えて、次を確認する。

| No | 確認内容 |
|----|----------|
| 1 | すべてのテーブルが対応エンティティを持つか。 |
| 2 | 主キー・外部キーが定義されているか。 |
| 3 | 共通カラムが全テーブルにあるか。 |
| 4 | 命名規則に従っているか。 |

## 7. 小規模（規模S）での簡略化

規模Sではテーブル一覧と個別ファイルを1ファイルにまとめてもよい。
