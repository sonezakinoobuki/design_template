# 運用設計書作成ガイド

本ガイドは、DOC-501 運用設計書の各項目に何をどこまで書くかを説明する。共通のルールは設計書作成規約（STD-003）に従う。

## 1. この設計書の役割

**稼働後のシステムを、誰が、いつ、どう見守り、どう戻すか。**

| 項目 | 内容 |
|------|------|
| 目的 | 本番稼働後の運用（監視・バックアップ・障害対応・定常作業）を定義する |
| 書かないこと | システム構成そのもの（→ DOC-201）、リリース作業の手順（→ DOC-502） |
| 作成条件 | 本番運用を行うシステム |
| 要否 | 条件付き必須（規模Sは推奨） |
| ファイル単位 | プロジェクトで1ファイル |
| テンプレート | [運用設計書_テンプレート](../02_テンプレート/運用/運用設計書_テンプレート.md) |

## 2. 作成の流れ

| 項目 | 内容 |
|------|------|
| 作成する工程 | 運用 |
| 作成前に読むもの（入力情報） | DOC-104 非機能要件定義書、DOC-201 システム構成設計書 |
| この設計書が正として定義するもの | 運用体制、監視項目と閾値、ジョブスケジュール、バックアップ・リストア手順、障害対応フロー、定常運用作業、ログ運用 |
| 関連設計書 | DOC-201、DOC-502 |

## 3. 項目別の記載ガイド

記載例は、共通の題材「個人向けタスク管理Webアプリ TaskNote」に基づく（03_記載例 参照）。要否・情報源の記号は設計書項目定義書（STD-004）2.2 に従う。

| No | 項目 | 記載内容 | 要否 | 情報源 | 記載例 |
|----|----|----|----|----|----|
| 4.1 | 運用体制 | 運用担当、連絡体制、対応時間帯 | ◎ | 正 | 運用担当｜本人｜メール｜平日 9:00〜18:00 |
| 4.2 | 監視 | 監視項目、閾値、検知時の通知先・対応 | ◎ | 正 | APIのエラー率｜5分間で5%超｜メール｜ログを確認する |
| 4.3 | ジョブスケジュール | バッチ（BAT）の実行スケジュール、実行順序 | ○ バッチあり | 正 | BAT-001｜毎日 8:00｜1番目｜翌日に手動で再実行 |
| 4.4 | バックアップ・リストア | 対象、頻度、保持世代、リストア手順 | ◎ | 正（方式は参照(DOC-201)） | データベース｜日次｜7世代｜管理画面から指定時点に復元 |
| 4.5 | 障害対応 | 障害レベル、対応フロー、復旧手順 | ◎ | 正 | レベル1｜全利用者が使えない｜即時対応｜本人 |
| 4.6 | 定常運用作業 | 日次・月次などの作業（OPS ID）、手順 | ○ 該当時 | 正 | OPS-001｜依存ライブラリの更新｜月次｜更新して CI を確認 |
| 4.7 | ログ運用 | ログの保管期間、ローテーション、参照方法 | ◎ | 正（出力方針は参照(DOC-201)） | アプリケーションログ｜30日｜日次｜クラウドのログ画面 |

## 4. 書き方のポイント

- 「誰が、いつ、何を見て、何をするか」まで書く。監視項目だけでは運用できない。
- バックアップは取得方法だけでなく、リストア手順を必ず書き、一度は試す。

## 5. よくある誤り

- システム構成そのものを書く → システム構成設計書を参照する。

## 6. レビュー観点

設計書作成規約（STD-003）14.2 の共通レビュー観点に加えて、次を確認する。

| No | 確認内容 |
|----|----------|
| 1 | すべての監視項目に通知先と対応があるか。 |
| 2 | リストア手順が試されているか。 |
| 3 | 非機能要件（可用性・運用）と矛盾しないか。 |

## 7. 小規模（規模S）での簡略化

規模Sでは、監視・バックアップ・障害対応の3項目だけでよい。
