# API設計書作成ガイド

本ガイドは、DOC-203 API設計書の各項目に何をどこまで書くかを説明する。共通のルールは設計書作成規約（STD-003）に従う。

## 1. この設計書の役割

**API は、何を受け取り、何を返し、失敗したらどう応答するか。**

| 項目 | 内容 |
|------|------|
| 目的 | システムが提供する API のインターフェース（入出力・振る舞い・エラー）を定義する |
| 書かないこと | API 内部の処理手順（→ DOC-301）、外部システムの API を利用する側の取り決め（→ DOC-205） |
| 作成条件 | APIを提供するシステム |
| 要否 | 条件付き必須 |
| ファイル単位 | API一覧で1ファイル、API（またはリソース）ごとに1ファイル。OpenAPI 等の機械可読定義がある場合はそれを正とし、本書から参照する |
| テンプレート | [API一覧_テンプレート](../02_テンプレート/基本設計/API一覧_テンプレート.md)、[API設計書_テンプレート](../02_テンプレート/基本設計/API設計書_テンプレート.md) |

## 2. 作成の流れ

| 項目 | 内容 |
|------|------|
| 作成する工程 | 基本設計 |
| 作成前に読むもの（入力情報） | DOC-103 機能一覧、DOC-204 DB設計書 |
| この設計書が正として定義するもの | API一覧、エンドポイント／操作、リクエスト・レスポンス定義、ステータス・エラーコード、認証・認可要件 |
| 関連設計書 | DOC-202、DOC-204、DOC-301、DOC-402 |

## 3. 項目別の記載ガイド

記載例は、共通の題材「個人向けタスク管理Webアプリ TaskNote」に基づく（03_記載例 参照）。要否・情報源の記号は設計書項目定義書（STD-004）2.2 に従う。

### 一覧ファイル（API一覧.md）

| No | 項目 | 記載内容 | 要否 | 工程 | 情報源 | 記載例 |
|----|----|----|----|----|----|----|
| 4.1 | API一覧 | API ID、API名、メソッド・パス（または操作名）、概要、対応機能、公開範囲（内部／外部） | ◎ | 基 | 正 | API-001｜ログイン｜POST｜/auth/login｜会員を認証しトークンを返す｜FNC-002｜内部 |
| 4.2 | 共通仕様 | ベースURL、通信方式、データ形式、文字コード、日時形式、ページング、バージョニング | ◎ | 基 | 正 | データ形式：JSON、日時形式：ISO 8601（UTC） |
| 4.3 | 共通認証・認可 | 認証方式の適用方法 | ◎ | 基 | 参照(DOC-207) | Authorization ヘッダーにトークンを付与。API-001・API-002 は認証不要 |
| 4.4 | 共通エラー形式 | エラー応答の構造、ステータスコードの使い分け、共通エラーコード | ◎ | 基 | 正 | {"code": "E002", "message": "..."}｜401：認証エラー |
| 4.5 | 機械可読定義 | OpenAPI などの定義ファイルの場所（ある場合はそれを正とする） | △ | 基 | 正 | openapi.yaml |

### 個別ファイル（API設計書_API-xxx.md）

| No | 項目 | 記載内容 | 要否 | 工程 | 情報源 | 記載例 |
|----|----|----|----|----|----|----|
| 4.1 | API概要 | 目的、対応機能（FNC）、呼び出し元（SCR、外部） | ◎ | 基 | 参照(DOC-103) | API-001｜ログイン｜会員を認証する｜FNC-002｜SCR-001 |
| 4.2 | エンドポイント | メソッド、パス、または操作名 | ◎ | 基 | 正 | POST｜/auth/login |
| 4.3 | 認可 | 実行可能なロール、データ単位のアクセス制御 | ◎ | 基 | 参照(DOC-207) | 認証不要｜— |
| 4.4 | リクエスト | 項目、型、必須、ドメイン、API固有の制約、説明 | ◎ | 基 | 正（ドメインは参照(DOC-105)） | 1｜メールアドレス｜email｜ボディ｜string｜必須｜メールアドレス｜—｜ログインID |
| 4.5 | レスポンス | 正常時の項目、型、説明、データ出所 | ◎ | 基 | 正 | 1｜トークン｜token｜string｜以降のAPIで使う｜— |
| 4.6 | エラー | エラーコード、HTTPステータス、発生条件、メッセージID | ◎ | 基 | 正（文言は参照(DOC-208)） | E002｜401｜メールアドレスまたはパスワードが誤り｜MSG-E002 |
| 4.7 | 振る舞い | 冪等性、副作用（データ更新）、同期・非同期、性能目標 | ◎ | 基 | 正 | 冪等性：なし／副作用：最終ログイン日時を更新 |
| 4.8 | 処理詳細 | 処理設計書（PRC）への参照 | ○ 該当時 | 詳 | 参照(DOC-301) | PRC-001｜認証処理 |
| 4.9 | 使用例 | リクエスト・レスポンスの例 | △ | 基 | 正 | POST /auth/login のリクエストとレスポンスの例 |

## 4. 書き方のポイント

- 呼び出し側（画面・外部）が API を使うために必要な情報をすべて書く。内部処理は書かない。
- エラーは「エラーコード・HTTPステータス・発生条件」の組で列挙する。画面設計書はこのコードを参照する。
- OpenAPI などの定義ファイルがある場合はそれを正とし、設計書には参照と補足だけを書く。二重管理を避ける。
- 副作用（データを更新するか）と冪等性（同じ要求を繰り返して安全か）を必ず書く。

## 5. よくある誤り

- テーブル定義を転記する → テーブルID で参照する。
- 認証方式の詳細を API ごとに書く → セキュリティ設計書を参照する。

## 6. レビュー観点

設計書作成規約（STD-003）14.2 の共通レビュー観点に加えて、次を確認する。

| No | 確認内容 |
|----|----------|
| 1 | すべてのリクエスト項目に型・必須・ドメインがあるか。 |
| 2 | 想定されるエラーが網羅されているか（入力不正・認証・権限・存在しない・競合）。 |
| 3 | 画面設計書の「呼び出すAPI」と整合しているか。 |

## 7. 小規模（規模S）での簡略化

規模Sでは API一覧と個別ファイルを1ファイルにまとめてもよい。
