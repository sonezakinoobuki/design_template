# テスト仕様書作成ガイド

本ガイドは、DOC-402 テスト仕様書の各項目に何をどこまで書くかを説明する。共通のルールは設計書作成規約（STD-003）に従う。

## 1. この設計書の役割

**何を、どういう手順で確かめ、何が起きれば合格か。**

| 項目 | 内容 |
|------|------|
| 目的 | テストケース（前提条件・手順・期待結果）を定義する |
| 書かないこと | 設計内容の再記述（設計書のIDを参照する） |
| 作成条件 | 常に |
| 要否 | 必須 |
| ファイル単位 | テストレベル × 対象機能（または画面・API）単位 |
| テンプレート | [テスト仕様書_テンプレート](../02_テンプレート/テスト/テスト仕様書_テンプレート.md) |

## 2. 作成の流れ

| 項目 | 内容 |
|------|------|
| 作成する工程 | テスト |
| 作成前に読むもの（入力情報） | DOC-401 テスト計画書、各設計書（要件・画面・API・処理など） |
| この設計書が正として定義するもの | テストケースID、テスト対象ID、観点、前提条件、手順、期待結果、実施結果 |
| 関連設計書 | DOC-401、DOC-403、テスト対象の各設計書 |

## 3. 項目別の記載ガイド

記載例は、共通の題材「個人向けタスク管理Webアプリ TaskNote」に基づく（03_記載例 参照）。要否・情報源の記号は設計書項目定義書（STD-004）2.2 に従う。

| No | 項目 | 記載内容 | 要否 | 情報源 | 記載例 |
|----|----|----|----|----|----|
| 4.1 | テスト対象 | テストレベル、対象の要素ID（SCR、API、PRC、NFR など） | ◎ | 参照(各設計書) | 結合｜SCR-001、API-001 |
| 4.2 | テストケース | TST ID、観点、前提条件、テストデータ、手順、期待結果 | ◎ | 正 | TST-001｜正常系｜会員登録済み｜test@example.com｜正しいパスワードでログイン｜タスク一覧画面に遷移する｜REQ-002 |
| 4.3 | 検証対象の要件 | テストケースごとの REQ／NFR ID | ◎ | 参照(DOC-101、DOC-104) | REQ-002 |
| 4.4 | 実施結果 | 実施日、実施者、結果（合格／不合格）、不具合ID | ◎ | 正 | TST-001｜2027-02-01｜本人｜合格｜— |

## 4. 書き方のポイント

- 期待結果は、誰が実施しても合否が同じになるよう具体的に書く。
- すべてのテストケースに検証対象の要件ID を書く。トレーサビリティマトリクスの元になる。
- 観点は、正常系・異常系・境界値・権限を意識して洗い出す。
- 自動テストがある場合は、テストコードの場所を書き、手順を簡略化してよい。

## 5. よくある誤り

- 設計書の内容を転記する（要素ID で参照する）。
- 「正しく表示されること」のような曖昧な期待結果。

## 6. レビュー観点

設計書作成規約（STD-003）14.2 の共通レビュー観点に加えて、次を確認する。

| No | 確認内容 |
|----|----------|
| 1 | すべての要件・受入条件にテストケースがあるか。 |
| 2 | 異常系・境界値の観点が漏れていないか。 |
| 3 | 期待結果が判定可能か。 |

## 7. 小規模（規模S）での簡略化

規模Sでは、テスト計画を冒頭に統合し、主要な機能ごとに1ファイルでよい。
