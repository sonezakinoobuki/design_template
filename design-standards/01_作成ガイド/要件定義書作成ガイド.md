# 要件定義書作成ガイド

本ガイドは、DOC-101 要件定義書の各項目に何をどこまで書くかを説明する。共通のルールは設計書作成規約（STD-003）に従う。

## 1. この設計書の役割

**システムは、誰のために、何を満たさなければならないか。**

| 項目 | 内容 |
|------|------|
| 目的 | システムが満たすべき要件（業務要件・機能要件の概要）を定義する |
| 書かないこと | 機能の詳細な分解（→ DOC-103）、画面やAPIの仕様（→ 基本設計） |
| 作成条件 | 常に |
| 要否 | 必須 |
| ファイル単位 | プロジェクトで1ファイル（大規模はサブシステム単位で分割可） |
| テンプレート | [要件定義書_テンプレート](../02_テンプレート/要件定義/要件定義書_テンプレート.md) |

## 2. 作成の流れ

| 項目 | 内容 |
|------|------|
| 作成する工程 | 要件定義 |
| 作成前に読むもの（入力情報） | DOC-001 プロジェクト概要書 |
| この設計書が正として定義するもの | 業務要件、機能要件（概要）、利用者・利用シーン、制約・前提、要件の優先度 |
| 関連設計書 | DOC-102、DOC-103、DOC-104、DOC-105 |

## 3. 項目別の記載ガイド

記載例は、共通の題材「個人向けタスク管理Webアプリ TaskNote」に基づく（03_記載例 参照）。要否・情報源の記号は設計書項目定義書（STD-004）2.2 に従う。

| No | 項目 | 記載内容 | 要否 | 情報源 | 記載例 |
|----|----|----|----|----|----|
| 4.1 | 利用者・アクター | 利用者の種類、特徴、人数規模 | ◎ | 正 | 会員｜タスクを管理したい個人｜〜100人 |
| 4.2 | 利用シーン | 主要な利用シーン（ユーザーストーリー、ユースケース） | ◎ | 正 | 会員として、期限付きでタスクを登録したい。なぜなら期限切れを防ぎたいから |
| 4.3 | 業務要件 | 業務として実現したいこと | ◎ | 正 | 期限が近いタスクを一覧で確認できる |
| 4.4 | 機能要件 | 要件ID（REQ）、要件内容、理由、優先度、受入条件 | ◎ | 正 | REQ-001｜会員はタスクを登録・確認できる｜紙のメモをやめるため｜高｜タスクを登録し、一覧に表示される |
| 4.5 | 業務ルール | 要件レベルの業務ルール・制約（例：注文は在庫数を超えられない） | ○ 該当時 | 正 | 1｜他の会員のタスクは参照できない｜REQ-002 |
| 4.6 | 非機能要件 | DOC-104 を統合する場合のみ | ○ 規模S | 正 | （規模S）可用性：夜間停止可 |
| 4.7 | データ要件 | DOC-105 を統合する場合のみ | ○ 規模S | 正 | （規模S）会員・タスクの2エンティティ |
| 4.8 | 対象外要件 | 今回は実現しないと決めたこと | ◎ | 正 | 1｜タスクの共有機能｜初回リリースでは個人利用に限定するため |

## 4. 書き方のポイント

- 要件は「誰が」「何を」できるかで書き、画面やボタンなど実現手段は書かない。
- 1つの要件ID には1つの要件だけを書く（1項目1情報）。
- 受入条件は、テストで合否を判定できる形で書く。テスト仕様書の期待結果の元になる。
- 対象外要件を書くと、スコープの合意が明確になる。

## 5. よくある誤り

- 「ログインボタンを押すと〜」のように画面操作を書く → 画面設計書に書く。
- 「高速に動作すること」のような測れない要件 → 非機能要件として目標値を書く。

## 6. レビュー観点

設計書作成規約（STD-003）14.2 の共通レビュー観点に加えて、次を確認する。

| No | 確認内容 |
|----|----------|
| 1 | すべての要件に ID・優先度・受入条件があるか。 |
| 2 | プロジェクト概要書の目的・スコープと矛盾しないか。 |
| 3 | 実現手段（画面・技術）を書いていないか。 |

## 7. 小規模（規模S）での簡略化

規模Sでは非機能要件（4.6）とデータ要件（4.7）を統合してよい。
