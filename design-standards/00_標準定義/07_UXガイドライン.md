# UXガイドライン

## 1. 目的

本書は、UI を持つアプリの**使い勝手と振る舞いのルール**（画面の構成の考え方、操作の流れ、入力フォーム、フィードバック、エラー時の振る舞い、文言、操作のアクセシビリティ）を、特定の言語・フレームワークに依存しない形で定義する。

画面設計書（DOC-202）の「イベント」「エラー時の振る舞い」「画面の状態」を書くときに、毎回振る舞いを一から考えずに済むようにし、アプリ全体で操作感をそろえることが狙いである。

本書のルールは標準の既定値である。アプリに合わせて変えてよい（STD-001 6.2）。ただし、データの消失を防ぐルール（本書 6.3、7.5）とアクセシビリティ（本書 12章）は下げないことを推奨する。

## 2. 対象範囲

| 区分 | 内容 |
|------|------|
| 対象 | Web アプリ、スマートフォンアプリ、デスクトップアプリの画面の振る舞いと文言の書き方 |
| 対象外 | 色・文字・余白などの見た目（→ STD-006）、個々のメッセージ文言の定義（→ DOC-208）、ユーザー調査・ユーザビリティテストの実施手順 |

本書と STD-006 デザインガイドラインの役割分担は、STD-006 2章の表に従う。

## 3. 前提・制約

- アクセシビリティの基準は WCAG 2.2 レベル AA とする（STD-006 と同じ）。
- 文言は日本語を前提とする。多言語対応するアプリでは、文言をメッセージ定義書（DOC-208）で一元管理し、画面に直接書かない。
- OS 標準のガイドライン（iOS、Android、Windows、macOS）の操作慣習と本書が異なる場合は、OS の慣習を優先する（例：戻る操作、設定画面の構成）。

## 4. UX の基本原則

設計で迷ったときは、次の原則で判断する。各章のルールはこの原則を具体化したものである。

| No | 原則 | 意味 | 具体化した章 |
|----|------|------|--------------|
| 1 | 今の状態が分かる | 利用者は、今どこにいて、何が起きているかを常に知ることができる | 5.3、8章 |
| 2 | 利用者の言葉を使う | 画面の言葉は、開発側の用語ではなく利用者の業務・生活の言葉にする | 11章 |
| 3 | やり直せる | 誤った操作は取り消せる。取り消せない操作は事前に確認する | 6.3 |
| 4 | 一貫している | 同じ意味のものは、同じ場所・同じ言葉・同じ振る舞いにする | 5章、6.1 |
| 5 | 誤りを起こさせない | 誤りを知らせるより先に、誤りが起きにくい入力方法にする | 7章 |
| 6 | 覚えなくてよい | 前の画面の情報を覚えておかなくても操作できる | 5.2、7.3 |
| 7 | 目的に集中できる | 1画面は1つの目的に絞り、目的に関係しない情報・操作を置かない | 5.1 |
| 8 | 回復の道を示す | エラーでは、何が起きたかと、次に何をすればよいかを示す | 9章 |
| 9 | 誰でも使える | 視覚・聴覚・運動機能・利用環境にかかわらず操作できる | 12章 |

## 5. 情報設計

### 5.1 画面の単位

| No | ルール |
|----|--------|
| 1 | 1画面は1つの目的（利用者が達成したいこと1つ）に対応させる。画面の目的は画面設計書の「画面概要」に1文で書けることを目安とする |
| 2 | 1画面の主操作は1つとする（STD-006 5.2 No.1 と対応） |
| 3 | 業務データを扱う画面は「一覧 → 詳細 → 編集」の型を基本とする。登録と編集は同じ画面構成にする |
| 4 | 頻繁に使う情報・操作ほど上（左）に置く。めったに使わない操作は「その他」メニューにまとめる |

### 5.2 ナビゲーション

| No | ルール |
|----|--------|
| 1 | 主要な画面には、どの画面からも2回以内の操作で到達できるようにする |
| 2 | 階層は3段以内とすることが望ましい。4段以上になる場合はパンくずリストを表示する |
| 3 | グローバルナビの項目は7個以内とする。超える場合はグループ化する |
| 4 | ナビゲーションの項目名と、遷移先の画面タイトルを一致させる |
| 5 | Web アプリでは、画面ごとに固有の URL を持たせ、ブックマーク・共有・ブラウザの戻るで同じ状態に戻れるようにする。一覧の検索条件・ページ番号も URL に含めることが望ましい |
| 6 | ブラウザ・OS の「戻る」操作を無効にしてはならない |

### 5.3 現在地の表示

- 画面タイトルを画面上部に表示し、ブラウザのタブ名（ページタイトル）にも「画面名 | アプリ名」の形で設定する。
- ナビゲーションで現在の画面に該当する項目を選択状態にする。
- 複数の手順に分かれる操作では、全体の手順数と現在の位置を表示する（例：「2 / 4 お届け先の入力」）。

### 5.4 名前の付け方

画面名・メニュー名・項目名は用語集（DOC-003）に定義した表記を使う。同じものを画面ごとに違う名前で呼んではならない（例：「会員」と「ユーザー」を混在させない）。

## 6. 操作の流れ

### 6.1 操作の配置

| No | ルール |
|----|--------|
| 1 | 画面全体に対する主操作（保存、新規作成）はページヘッダーの右、またはフォームの末尾に置く。アプリ内で位置を統一する |
| 2 | ボタンを並べる場合、主ボタンと副ボタンの左右の並びをアプリ内で統一する。既定は「副（キャンセル）を左、主を右」とする（OS の慣習が異なる場合はそれに従う） |
| 3 | 一覧の行に対する操作（編集、削除）は、行の右端または行を開いた先に置く |
| 4 | 削除などの破壊的操作は、主操作と離して置き、危険ボタン（STD-006 9.1）にする |

### 6.2 複数手順の操作

- 1画面の入力項目が多い場合（目安として 10 項目超）は、手順に分ける、またはグループに分けて見出しを付ける。
- 手順に分ける場合は、前の手順に戻っても入力内容を保持する。
- 最後の手順の前に確認画面を置くかは、操作の重さで決める。お金・契約・外部への送信が伴う操作には確認画面を置く。それ以外は置かないことが望ましい（手順を増やさないため）。

### 6.3 取り消しと確認

| 操作の性質 | 振る舞い | 例 |
|------------|----------|-----|
| 取り消せる操作 | 確認せずに実行し、完了の通知に「元に戻す」を付ける（5秒以上表示） | アーカイブ、既読化、ゴミ箱への移動 |
| 取り消せない操作 | 実行前に確認ダイアログを出す | 完全削除、送信、決済、解約 |
| 取り消せず影響が大きい操作 | 確認ダイアログで対象名の入力など、意図した操作であることを確かめる | アカウント削除、プロジェクトの完全削除 |

- 確認ダイアログを多用してはならない。確認が多いと読まずに押されるようになるため、取り消せる操作には「元に戻す」を使う。
- 確認ダイアログの文言は 11.4 に従う。

### 6.4 二重実行の防止

- 送信・保存の操作を受け付けたら、完了するまでそのボタンを処理中の状態（STD-006 9.2）にし、再度押せないようにする。
- 通信が途切れて再送する場合も、同じ処理が二重に実行されないようにする（サーバー側の方式は API 設計書 DOC-203 で定義する）。

### 6.5 中断と離脱

- 入力途中で画面を離れようとした場合（他画面への遷移、タブを閉じる）、未保存の変更があれば警告する。
- 入力に 5 分以上かかることが想定されるフォームは、自動保存または下書き保存を用意することが望ましい。
- セッションの有効期限が切れた場合は、再ログイン後に元の画面と入力内容に戻れるようにすることが望ましい。

## 7. 入力フォーム

### 7.1 項目の設計

| No | ルール |
|----|--------|
| 1 | 入力項目は必要最小限にする。後で聞けるもの・システムが推定できるものは聞かない |
| 2 | 選択肢が 5 個以下ならラジオボタン、6 個以上ならセレクトボックス、20 個以上なら検索付きの選択にする |
| 3 | オン・オフの設定で即時に反映されるものはスイッチ、保存ボタンで確定するものはチェックボックスにする |
| 4 | 日付・郵便番号・電話番号は、入力形式を利用者に合わせさせず、システム側で吸収する（全角・半角、ハイフンの有無を許容する） |
| 5 | 1つの意味の値は1つの入力欄で受け付ける（電話番号を3欄に分けない） |
| 6 | 入力欄には適切な入力の種類（メール、数値、電話）と自動補完の指定をし、端末のキーボード・自動入力が使えるようにする |
| 7 | 初期値は、多くの利用者が選ぶ値がはっきりしている場合だけ設定する。同意・有料オプションに初期値でチェックを入れてはならない |

### 7.2 必須・任意の表示

- 必須か任意かを、ラベルの横に文字で表示する。記号（＊）だけで示さない。
- 必須の項目が多いフォームでは「任意」だけを表示し、フォームの先頭に「任意と書かれていない項目は必須です」と書いてもよい。どちらの方式にするかはアプリで統一し、画面一覧の共通仕様に書く。

### 7.3 説明の出し方

- 入力のルール（文字数、使える文字）は、入力前に見える位置（ラベルの下のヘルプ文）に書く。エラーになってから初めて知らせてはならない。
- パスワードのように条件が多い項目は、条件の一覧を表示し、満たした条件を入力中に示すことが望ましい。

### 7.4 検証のタイミング

| タイミング | 行う検証 | 備考 |
|------------|----------|------|
| 入力中 | 行わない（文字数カウンター・パスワード条件の表示を除く） | 入力途中でエラーを出さない |
| 項目から離れたとき | 形式のチェック（必須、桁数、形式） | 一度エラーになった項目は、以降は入力中に再検証して、直ったらすぐエラーを消す |
| 送信時 | すべての項目の検証、サーバー側の検証（重複、業務ルール） | 画面とサーバーの両方で検証し、サーバーを正とする |

### 7.5 エラーの表示と入力の扱い

| No | ルール |
|----|--------|
| 1 | エラーは該当する項目の直下に表示する |
| 2 | 送信時にエラーがある場合は、フォームの先頭にエラーの件数と一覧（各項目へのリンク）を表示し、最初のエラー項目にフォーカスを移す |
| 3 | エラーになっても、利用者の入力内容を消してはならない。例外はパスワード・カード番号のセキュリティ上保持できない項目に限る |
| 4 | エラーが解消されたら、すぐに表示を消す |

## 8. フィードバック

### 8.1 応答時間と表示

| 処理にかかる時間 | 画面の振る舞い |
|------------------|----------------|
| 0.1 秒未満 | 特別な表示は不要。結果をすぐ反映する |
| 0.1〜1 秒 | 押したボタンを処理中の状態にする |
| 1〜10 秒 | スピナー、または読み込む領域にスケルトンを表示する |
| 10 秒以上 | 進捗バー（進み具合が分かる場合）と残り時間・件数を表示し、取り消しの手段を用意する。可能ならバックグラウンドで実行し、完了を通知する |

- 結果がほぼ確実に成功する操作（いいね、並べ替え）は、先に画面へ反映し、失敗したときに元に戻してエラーを知らせてもよい（楽観的更新）。お金・在庫・権限に関わる操作には使わない。

### 8.2 通知の使い分け

| 方法 | 使う場面 | 消え方 |
|------|----------|--------|
| 項目の近くの表示（インライン） | 特定の項目・領域に関する結果（入力エラー、その行の保存完了） | 原因が解消されたら消える |
| トースト | 操作の完了を短く知らせる（「保存しました」） | 5 秒程度で自動で消える。「元に戻す」付きは 5 秒以上 |
| バナー | 画面全体・アプリ全体に関わる状態（メンテナンス予告、オフライン、権限不足） | 状態が解消されるか、利用者が閉じるまで残る |
| ダイアログ | 利用者の判断が必要なもの（取り消せない操作の確認） | 利用者が選ぶまで残る |

- エラーをトーストだけで知らせてはならない。自動で消えると見落とされるため、エラーはインラインまたはバナーで残す。
- 1つの操作に対して複数の方法で同じことを知らせない。

### 8.3 完了後の画面

- 保存後にどの画面へ遷移するかをアプリ内で統一する。既定は「新規作成 → 作成したものの詳細画面」「編集 → 元の詳細画面」「削除 → 一覧画面」とする。
- 遷移後の画面で、操作の結果（作成されたもの、削除されたもの）が分かるようにする。

## 9. エラー時の振る舞い

### 9.1 エラーの種類と振る舞い

| 種類 | 伝えること | 画面の振る舞い |
|------|------------|----------------|
| 入力エラー | どの項目が、どう誤っているか、どう直せばよいか | 7.5 に従う |
| 業務エラー（重複、在庫切れ、期限切れ） | 何ができなかったか、理由、代わりにできること | 入力を保持し、該当箇所またはフォーム先頭に表示する |
| 権限エラー | この操作・画面は利用できないこと、利用するにはどうすればよいか（管理者への依頼） | 操作できないものは、できるだけ事前に非表示または無効にする |
| 対象が見つからない（404） | 対象が存在しない、または削除されたこと | 一覧画面・トップ画面へのリンクを表示する |
| 通信エラー | 接続できなかったこと、もう一度試せること | 入力を保持し、「再試行」ボタンを表示する。オフラインの場合はバナーで知らせる |
| セッション切れ | ログインし直す必要があること | 6.5 に従い、再ログイン後に元の画面へ戻す |
| システムエラー（想定外） | 問題が起きたこと、時間をおいて試すこと、問い合わせ先、問い合わせ用の番号 | 内部の情報（スタックトレース、SQL）を表示してはならない |

### 9.2 エラーを防ぐ

- 実行できない操作は、押した後にエラーを出すのではなく、事前に無効にし、無効の理由を近くに表示する（無効のボタンだけでは理由が分からないため）。
- 選択肢で済むものは自由入力にしない。

## 10. 特別な状態の画面

| 状態 | 表示すること |
|------|--------------|
| 初めて使うとき（データ 0 件） | この画面で何ができるかの説明と、最初の操作（「最初のタスクを作成」）のボタン |
| 検索・絞り込みの結果が 0 件 | 条件に合うものがないことと、条件の解除・変更の手段 |
| 読み込み中 | 8.1 に従う |
| 読み込みの失敗 | 9.1 の通信エラーに従い、画面のほかの部分は操作できるままにする |
| 一部のデータだけ取得できない | 取得できた部分を表示し、取得できない部分にだけエラーと再試行を表示する |

### 10.1 一覧・検索

| No | ルール |
|----|--------|
| 1 | 件数が多い一覧は、総件数を表示する |
| 2 | 業務データの一覧はページ送りを既定とする（位置を URL で共有でき、件数が分かるため）。無限スクロールはタイムラインのように終わりを意識しない一覧に限る |
| 3 | 並び順の初期値を決め、現在の並び順を表示する |
| 4 | 絞り込み中であることと、適用中の条件を一覧の上に表示し、まとめて解除できるようにする |
| 5 | 検索語は、検索後も入力欄に残す |

## 11. 文言

個々のメッセージの文言はメッセージ定義書（DOC-208）で定義する。本章はその**書き方**を定める。

### 11.1 トーン

| 項目 | ルール |
|------|--------|
| 文体 | 利用者向けの文言は敬体（です・ます）とする（STD-003 9章） |
| 主語 | 利用者を主語にした書き方にする。システムの内部の都合を書かない |
| 長さ | 1文は 40 文字以内を目安とする。1つのメッセージは2文以内が望ましい |
| 感情 | 謝罪・感嘆符は多用しない。謝罪はシステム側に原因がある場合だけ1回にする |
| 責めない | 利用者の誤りを責める言い方をしない（「不正な入力です」ではなく「半角数字で入力してください」） |

### 11.2 ボタン・リンクのラベル

| No | ルール | 悪い例 | 良い例 |
|----|--------|--------|--------|
| 1 | 何が起きるかが分かる動詞にする | OK、はい | 保存する、削除する |
| 2 | 同じ操作には同じラベルを使う | 画面により「登録」「保存」「確定」が混在 | 「保存する」に統一 |
| 3 | リンクは遷移先が分かる言葉にする | こちら、詳しくはここ | 料金プランを見る |
| 4 | 簡潔にする（全角 10 文字以内が目安） | 入力した内容で登録を実行する | 登録する |

ラベルは「〜する」形か名詞形（「保存」）のどちらかにアプリで統一する。

### 11.3 メッセージの型

| 種類 | 型 | 例 |
|------|-----|-----|
| 入力エラー | 直し方 | 「メールアドレスを入力してください」「8 文字以上で入力してください」 |
| 業務エラー | 起きたこと＋理由＋次にできること | 「このメールアドレスは登録済みです。ログインするか、別のメールアドレスを入力してください」 |
| システムエラー | 起きたこと＋次にできること＋問い合わせ情報 | 「保存できませんでした。時間をおいてもう一度お試しください。（エラー番号：E-1234）」 |
| 完了 | 何が完了したか | 「タスクを保存しました」 |
| 確認 | 11.4 に従う | — |
| 空状態 | 状態＋最初の操作 | 「まだタスクはありません。最初のタスクを作成しましょう」 |

### 11.4 確認ダイアログ

| 部分 | ルール | 例 |
|------|--------|-----|
| タイトル | 操作と対象を疑問形で書く | 「タスク『請求書を送る』を削除しますか？」 |
| 本文 | 実行した結果どうなるか、取り消せるか | 「削除したタスクは元に戻せません」 |
| 実行ボタン | 操作名にする（「はい」「OK」にしない）。破壊的操作は危険ボタン | 「削除する」 |
| 取り消しボタン | 「キャンセル」 | 「キャンセル」 |

### 11.5 使わない表現

| 使わない表現 | 理由 | 代わりの書き方 |
|--------------|------|----------------|
| 開発側の用語（レコード、フラグ、セッション、ID、null） | 利用者に意味が通じない | 利用者の業務の言葉（タスク、ログイン状態） |
| エラーコードだけのメッセージ | 何をすればよいか分からない | 11.3 の型で書き、番号は補足として添える |
| 二重否定（「〜しないと〜できません」） | 読み違えやすい | 「〜すると〜できます」 |
| 曖昧な言葉（「しばらく」「一部」「正しく」） | 判断できない | 具体的な時間・対象・条件 |

### 11.6 日付・時刻・数値

表記は STD-003 9章に従う。そのうえで、利用者向けの画面では次の表記を使ってよい。

| 対象 | 表記 |
|------|------|
| 直近の日時 | 1 分未満は「たった今」、1 時間未満は「〇分前」、24 時間未満は「〇時間前」。それ以上は日付。正確な日時は補足（ホバー、詳細）で示す |
| 日付 | 年が今年なら年を省略してよい（11月25日） |
| 金額 | 通貨記号または「円」を付け、3 桁区切り（1,000円） |

## 12. 操作のアクセシビリティ

見た目に関する基準は STD-006 11章で定義する。本章は操作・読み上げに関する基準を扱う。

| No | 基準 | 内容 |
|----|------|------|
| 1 | キーボードで操作できる | すべての操作をキーボードだけで行える。マウスのホバーでしか出ない情報・操作を作らない |
| 2 | フォーカスの順序が自然 | フォーカスは見た目の順（上から下、左から右）に移動する |
| 3 | フォーカスを閉じ込めない | モーダルを開いたらモーダル内にフォーカスを移し、閉じたら開いた元の部品に戻す。Esc キーで閉じられる |
| 4 | 名前が読み上げられる | すべての入力欄にラベル、アイコンだけのボタンに読み上げ用の名前を付ける |
| 5 | 状態の変化が伝わる | トースト・エラー・検索結果件数の変化を、読み上げソフトに通知する |
| 6 | 見出しで構造が分かる | 画面タイトルを最上位の見出しにし、見出しの階層を飛ばさない |
| 7 | 時間制限を緩められる | 時間制限のある操作は、期限前に警告し、延長できるようにする |
| 8 | 複雑な操作に代替手段がある | ドラッグ・スワイプ・複数指の操作には、ボタンなど1回の操作で済む代替手段を用意する |
| 9 | 言語が指定されている | 画面の言語（`lang="ja"` 相当）を指定する |
| 10 | 認証が記憶に頼らない | パスワード入力欄への貼り付け・パスワード管理ツールの自動入力を妨げない |

## 14. レビュー観点

画面設計書・実装のレビューで、次を確認する。

| No | 観点 | 確認内容 |
|----|------|----------|
| 1 | 目的 | 画面の目的を1文で説明できるか。主操作が1つか |
| 2 | 現在地 | 画面タイトル・ナビの選択状態・手順の位置が表示されるか |
| 3 | 用語 | 画面名・ラベルが用語集の表記に従い、画面間で同じものを同じ名前で呼んでいるか |
| 4 | 取り消し | 破壊的操作に「元に戻す」または確認があるか。確認が多すぎないか |
| 5 | 二重実行 | 送信・保存が二重に実行されないか |
| 6 | 離脱 | 未保存の変更があるときに警告するか |
| 7 | フォーム | 必須・任意が文字で表示され、入力ルールが事前に分かるか |
| 8 | 入力の保持 | エラー時・通信失敗時に入力内容が消えないか |
| 9 | フィードバック | 1 秒以上かかる処理に読み込み表示があるか。エラーがトーストだけで消えないか |
| 10 | エラー | エラーに「何が起きたか」と「次に何をすればよいか」があるか。内部の情報を表示していないか |
| 11 | 特別な状態 | 0 件・読み込み中・読み込み失敗の表示が定義されているか |
| 12 | 文言 | ボタンが動詞か。「OK」「こちら」がないか。開発側の用語がないか |
| 13 | キーボード | キーボードだけで操作でき、フォーカスの順序が自然か。モーダルを Esc で閉じられるか |
| 14 | 読み上げ | 入力欄・アイコンボタンに名前があり、状態の変化が通知されるか |
