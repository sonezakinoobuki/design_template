# 第2段階 整合性チェック結果

| 項目 | 内容 |
|------|------|
| 実施日 | 2026-11-23 |
| 対象 | STD-002 設計書体系定義書 v0.1.0、STD-004 設計書項目定義書 v0.1.0 |
| 目的 | 各設計書の項目を洗い出した結果、設計書間で情報の重複・不足・責務の曖昧さがないかを確認する |

## 1. チェック方法

1. 全設計書の項目（STD-004）を並べ、同じ情報が複数の設計書で「正」になっていないかを確認した（重複チェック）。
2. 開発で必ず決める必要がある事項を列挙し、どの設計書にも「正」の置き場がないものを探した（不足チェック）。
3. 同じ情報を扱う設計書同士で、どこまでをどちらが書くかの境界を確認した（責務チェック）。

## 2. 指摘と対応

### 2.1 重複

| No | 指摘 | 関係する設計書 | 対応 |
|----|------|----------------|------|
| D-1 | 入力項目の型・桁・形式が、画面・API・DB の3か所で定義され、食い違うおそれがある | DOC-202、DOC-203、DOC-204 | DOC-105 に「データ項目辞書（ドメイン）」を設け、型・桁・形式の論理定義の正とした。画面・API・DB はドメイン名を参照し、それぞれ固有の制約だけを書く |
| D-2 | 画面・API のそれぞれに「利用できるロール」を書くと、権限の全体像が分散する | DOC-202、DOC-203、DOC-207 | DOC-207 に「権限マトリクス（機能 × ロール）」を設けて正とした。画面・API は参照のみとする |
| D-3 | エラー時の内容が画面・API・メッセージ定義で重複しやすい | DOC-202、DOC-203、DOC-208 | 役割を分けた。エラーコードと発生条件 = DOC-203、画面での振る舞い = DOC-202、文言 = DOC-208 |
| D-4 | コード値（区分値）がDB設計書・用語集・API の列挙値で重複する | DOC-003、DOC-203、DOC-204 | 値と意味の論理定義を DOC-105「コード定義」に置き、DOC-204 は格納方式（物理）のみを扱うようにした |
| D-5 | 自システムが外部に公開する API の仕様が、API設計書と外部IF設計書の両方に書かれうる | DOC-203、DOC-205 | API の仕様は DOC-203 を正とし、DOC-205 には連携先ごとの運用上の取り決めのみを書く |

### 2.2 不足

| No | 指摘 | 対応 |
|----|------|------|
| G-1 | ログ出力、例外処理、トランザクション、日時・タイムゾーン、採番などの「共通方式」の置き場がない。DOC-302 は規模S・Mで任意のため、そこに置くと小規模で抜け落ちる | 必須の DOC-201 システム構成設計書に「共通方式」の章を追加した。DOC-302 はその実装先のみを書く |
| G-2 | 環境ごとの設定値の管理方式の置き場がない | DOC-201 に「設定値管理」を追加した（秘密情報の値は書かない） |
| G-3 | エンティティの状態遷移（例：注文ステータス）の置き場がない | DOC-105 に「状態遷移」を追加した |
| G-4 | バッチの実行スケジュールの置き場が曖昧（処理設計書か運用設計書か） | バッチの一覧と依存関係は DOC-301、実行スケジュールは DOC-501 を正とした |
| G-5 | データ移行の設計書がない。非機能要件で移行性は定義するが、移行の具体的な設計（変換仕様、手順、検証）を書く場所がない | 設計書の新設判断基準（STD-001 7.1）をすべて満たすため、DOC-503 移行設計書（条件付き必須：既存データ・システムからの移行がある場合）を新設した。設計書は全24種（第1段階の23種＋1）となる |
| G-6 | 非機能要件からテストへの追跡が定義されていない（追跡関係図に NFR → TST がない） | STD-002 8章の追跡関係に NFR → TST を追加し、DOC-402 にテストケースごとの REQ／NFR ID を必須項目とした |
| G-7 | 外部連携の秘密情報（APIキーなど）の扱いが未定義 | DOC-207「秘密情報の管理」で保管方式を定義し、各設計書には値を書かないこととした |

### 2.3 責務の境界

| No | 境界 | 決定 |
|----|------|------|
| B-1 | 業務フロー図と処理設計書 | 業務フロー図は人とシステムの役割分担（システムの外から見た流れ）、処理設計書はシステム内部の手順 |
| B-2 | 要件定義書の業務ルールと処理設計書の業務ルール | 要件定義書は「何を守るか」（例：在庫を超えて注文できない）、処理設計書は「どう判定するか」（判定条件・計算式） |
| B-3 | システム構成設計書とモジュール構成設計書 | システム構成はサーバー・サービスなど実行環境の構成と全体方針、モジュール構成はソフトウェア内部の分割と依存 |
| B-4 | 運用設計書とリリース手順書 | 運用設計書は恒常的な運用、リリース手順書はリリースという一時的な作業 |
